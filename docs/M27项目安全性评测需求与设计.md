# M27 项目安全性评测 — 需求与设计方案

> 状态：设计阶段（未写代码）
> 创建：2026-10-20
> 背景：当前 AI 项目评价（ai_summary / ai_use_cases / ai_risks / health_score）缺少**安全维度**——用户关心"这个项目会不会上传我的信息、有没有后门"。

---

## 1. 需求定义

### 1.1 用户问题

在决定"是否采用/克隆/运行一个开源项目"前，用户想知道：

| 问题 | 示例 |
|------|------|
| 是否会回传使用者信息？ | 遥测、埋点、上报 IP/设备/使用数据 |
| 是否留有后门？ | 隐藏的远程执行、硬编码回连地址 |
| 是否有恶意代码风险？ | 混淆代码、可疑 install 脚本、依赖混淆/抢注 |
| 供应链是否可信？ | 作者信誉、维护状态、依赖可信度 |

### 1.2 需求边界（必须明确）

- **这是"风险提示"，不是"安全保证"**。任何自动化评测都无法证明一个项目"绝对无后门"，输出必须带免责声明
- 不替代专业安全审计
- 评测结果需要**可解释**：每个风险项必须给出证据出处，不允许只给一个干巴巴的分数

---

## 2. 分级评测方案（核心设计）

### L1 — 资料级评测（默认，零下载、秒级）

**输入**（全部来自现有数据库，无需新增采集）：
- README 全文（`projects.readme_content`）
- 项目描述、作者/组织、语言、Star/Fork、健康分
- AI 已提取的依赖清单（`projects.ai_dependencies`）

**评测方式**：单次 LLM 调用，结构化输出。

**能发现什么**：
- README 中明示/暗示的遥测、数据收集、账号绑定、强制联网
- 要求的高危权限（文件系统、摄像头、键盘记录等）
- 作者匿名 + 代码不可见 + 二进制分发等可疑组合信号
- 许可证风险（非 OSI、附加限制条款）

**局限（必须在 UI 明示）**：只看文档，看不到代码里的实际行为。文档没写的恶意行为无法发现。

### L2 — 代码级深度审计（可选，重量级）

**触发**：用户在 L1 结果页点击"深度审计"，明确确认后执行。

**流程**：
1. 浅克隆（`--depth 1`）到临时目录（复用现有 clone 能力）
2. 静态扫描（本地规则，不调 LLM，毫秒级）：
   - 网络回传模式：硬编码 URL/IP、`fetch(`/`axios`/`requests.post` 指向非官方域
   - 危险 API：`eval`/`exec`/`child_process`/`Process::start`、`subprocess`、`Runtime.exec`
   - 混淆特征：超长 base64 串、十六进制字符串数组、乱码标识符密度
   - 安装脚本：`preinstall`/`postinstall`（package.json）、`setup.py` 执行体、build.rs 网络访问
   - 敏感文件访问：`.ssh`、`known_hosts`、浏览器 cookie 路径、钱包路径
   - 依赖混淆：依赖名与知名包拼写相似（typosquatting 词典比对）
3. 命中的代码片段（上下文 ±5 行）交给 LLM 研判，过滤误报
4. 输出合并到安全报告

**成本**：一次克隆 + 本地扫描 + 1-2 次 LLM 调用，分钟级。

---

## 3. 输出结构

### 3.1 安全评分模型

| 字段 | 类型 | 说明 |
|------|------|------|
| security_score | 0-100 | 综合安全分（100 = 未见风险信号） |
| risk_level | 枚举 | `safe` 安全 / `notice` 注意 / `risky` 风险 / `danger` 高危 |
| risk_items | 数组 | 每项：类别 + 严重程度 + 描述 + 证据出处 |
| telemetry | 布尔+说明 | 是否存在数据回传行为/声明 |
| level | `L1`/`L2` | 本次评测深度 |
| evaluated_at | 时间 | 评测时间 |
| disclaimer | 固定文案 | "自动化评测仅供参考，不构成安全保证" |

### 3.2 风险项类别（risk_items[].category）

| 类别 | 说明 |
|------|------|
| telemetry | 遥测/数据回传 |
| permission | 高危权限要求 |
| network | 可疑网络行为 |
| obfuscation | 代码混淆 |
| supply_chain | 供应链/依赖风险 |
| reputation | 作者/信誉信号 |
| license | 许可证风险 |
| install_script | 安装期执行代码 |

### 3.3 LLM 输出协议（JSON Schema 约束）

```json
{
  "security_score": 85,
  "risk_level": "notice",
  "telemetry": {"present": true, "detail": "README 声明收集匿名使用统计"},
  "risk_items": [
    {"category": "telemetry", "severity": "low", "detail": "...", "evidence": "README 第 X 节原文引用"}
  ]
}
```

## 4. 存储设计

按 AGENTS.md 归属：**仓库库** `os_compass.db`（随仓库切换，与项目数据同生命周期）。

方案：`projects` 表新增 3 列（复用现有表结构，与 ai_* 列风格一致）：

| 列 | 类型 | 说明 |
|----|------|------|
| `ai_security_score` | INTEGER | 0-100 |
| `ai_security_level` | TEXT | safe/notice/risky/danger |
| `ai_security_report` | TEXT | 完整 JSON 报告 |
| `ai_security_at` | TEXT | 评测时间 |

迁移：加入 `db.rs` missing_tables 同款 ALTER 兜底机制（或借 #体检 发现的"启动全量幂等执行 init_schema.sql"方案一并解决）。

L2 审计的克隆临时目录：系统临时目录，审计完删除，不落库。

## 5. UI 设计

### 5.1 项目详情页（主入口）

AI 报告/评价区域新增「安全评测」卡片：
- 未评测：「开始安全评测」按钮 + 说明文字（L1 秒级）
- 已评测：安全分 + 风险等级徽章（绿/黄/橙/红）+ 风险项折叠列表（每项可展开看证据）+ 「深度审计（L2）」按钮 + 评测时间 + 免责声明

### 5.2 项目列表（轻量透出）

已评测项目在行内显示风险等级小徽章（圆点色标即可），不占用新空间。

## 6. 实施任务拆分（预估）

| Task | 内容 | 预估 | 依赖 |
|------|------|------|------|
| T1 | DB 迁移 + 4 列 + Rust 结构体 | 1h | - |
| T2 | L1 Prompt 设计 + LLM 调用 + JSON 解析容错 | 2h | T1 |
| T3 | 后端命令 `evaluate_project_security` | 1h | T2 |
| T4 | 详情页安全评测卡片 UI + i18n | 2h | T3 |
| T5 | 列表页徽章 | 0.5h | T4 |
| T6 | L2 静态扫描引擎（规则库） | 4h | T1 |
| T7 | L2 克隆 + 扫描 + LLM 研判串联 | 2h | T6 |
| T8 | 测试（单测 + 已知恶意样本回归） | 2h | T5/T7 |

L1（T1-T5）约 5.5h 可先行交付；L2（T6-T8）约 8h 后置。

## 7. 验证方式

- 正面样本：选取知名良性项目（如 VSCode 类），确认不误报高危
- 负面样本：构造含遥测声明/可疑 postinstall 的测试项目，确认识别
- 回归：pnpm test + cargo check/clippy + 构建双验证（含 DLL 检查）
