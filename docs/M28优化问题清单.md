## OPT-01 看板视图：分类筛选不支持层级、不支持多选、选上级不含下级

### 现象

1. 筛选面板的分类下拉框是**平铺列表**（`KanbanView.tsx:288-290` 直接 `categories.map` 输出 `cat.name`），多级分类看不出层级关系；
2. 只能**单选**一个分类；
3. 选中某个上级分类时，**只匹配 `category_id` 精确相等**（`KanbanView.tsx:192`），下级分类里的项目不会被筛选出来——不符合"选上级=看整个分支"的直觉。

### 根因

- 前端过滤条件：`p.category_id === filterCategory`（精确匹配，无后代展开）
- 下拉框为原生 `<select>` 单选，无法表达多选与层级缩进

### 修复方案

1. 复用 `CategoryManager.tsx` 中已有的 `buildTree` 逻辑，把分类渲染为**带缩进的层级树**（复选框）；
2. 筛选值改为 `Set<number>` 多选；
3. 选中某分类时，**自动展开其后代分类集合**参与匹配（内存中递归收集后代 id）；
   - 交互上：勾选父分类自动级联勾选全部子分类（视觉上子项随父项联动），取消父分类时保留子分类已勾选状态还是一并清除——**建议级联联动（勾选父=全选子孙，取消父=取消子孙）**，与主流文件管理器一致，待确认；
4. 筛选计数徽标同步改为按勾选数统计。

### 影响评估

| 维度 | 评估 |
|------|------|
| 改动范围 | 仅 `KanbanView.tsx` 前端（过滤逻辑 + 筛选面板 UI） |
| 数据/接口 | 无需改后端 |
| 风险 | 低；注意 `hasActiveFilters` 计数逻辑同步调整 |
| 工作量 | 约 0.5 天 |

## OPT-02 项目详情：URL 缺复制按钮、不可点击跳转

### 现象

详情弹窗头部的项目 URL（`ProjectDetailDialog.tsx:729`）是纯文本 `<p>{project.url}</p>`：

- 想复制只能鼠标拖选，长 URL 容易选不全；
- 不能点击直接打开项目主页，要复制后手动粘贴到浏览器。

### 修复方案

1. URL 渲染为 `<a>` 超链接，点击经 Tauri `shell.open` 用**默认浏览器**打开（不走 WebView 内跳转）；
2. URL 右侧加**复制按钮**（`fa-copy` 图标按钮），点击写入剪贴板 + Toast「链接已复制」；
3. 复制成功反馈：图标短暂变为 ✓（约 1.5 秒恢复）。

### 影响评估

| 维度 | 评估 |
|------|------|
| 改动范围 | `ProjectDetailDialog.tsx` 头部区域；复用现有剪贴板/打开链接工具函数（项目内已有 `shell.open` 先例） |
| 风险 | 低 |
| 工作量 | < 0.5 天 |

## OPT-03 项目详情：标题与 URL 显示长度需要收敛

### 现象

头部标题 `<h1>` 与 URL `<p>` 目前无长度约束（无 `truncate`）。超长项目名或超长 URL 会撑破头部布局。

### 依赖关系

依赖 OPT-02 完成后实施——有了复制按钮和点击跳转，URL 不再需要完整可见，可以放心截断。

### 修复方案

1. 标题：`truncate` 单行截断 + `title` 属性悬停显示完整名；
2. URL：`truncate` 单行截断 + `title` 悬停显示完整地址；
3. 头部右侧操作按钮区（编辑/打开编辑器等）加 `flex-shrink-0`，保证长文本挤压时按钮不被压缩。

### 影响评估

| 维度 | 评估 |
|------|------|
| 改动范围 | `ProjectDetailDialog.tsx` 头部 2 行样式 |
| 风险 | 极低 |
| 工作量 | 随 OPT-02 顺带完成 |

## OPT-04 用户笔记纳入项目探索与向量检索依据

### 现状排查结论（重要）

| 子项 | 现状 |
|------|------|
| 项目探索（对话知识库） | ✅ **已包含笔记**：`explore.rs` 的 `load_materials` 会读取 `project_notes` 全部笔记拼接注入 Prompt（≤3000 字符截断） |
| 向量检索（语义搜索 / 相似项目匹配） | ❌ **未包含笔记**：`embedding.rs:282` 的 `build_project_embedding_text` 只拼接 `name + description + languages` |

即：**需要改的只是向量化文本来源，探索对话已经用了笔记。**

### 评估

| 评估点 | 结论 |
|--------|------|
| 收益 | 笔记里往往是用户实测结论（"这个项目在 Windows 下编译要加 X"），纳入后语义搜索和 M28 相似项目匹配能命中这些经验 |
| 安全性 | ✅ 无风险——笔记是 `project_notes` 表（用户主动撰写的内容）；真正的敏感区是 `project_user_info`（数据保险箱），**绝不纳入**，现有探索代码已遵守此红线 |
| 时效性 | ⚠️ 笔记更新后向量会过期，需要在**保存/删除笔记**时触发该项目重新向量化（1 次 Embedding 请求） |
| 成本 | 每次笔记变更多 1 次 Embedding 调用，可忽略 |
| 决策建议 | **建议做**：向量文本追加笔记摘要（前 500 字符即可，避免长笔记稀释名称/描述权重） |

### 修复方案（若采纳）

1. `build_project_embedding_text` 追加第四个参数：笔记摘要（前 500 字符）；
2. `project_notes` 的增删改命令完成后，异步触发 `generate_project_embeddings(project_id)`；
3. 存量项目：提示用户在 Embedding 配置后/笔记功能使用后，用看板「向量化全部」重建一次（一次性）。

### 影响评估

| 维度 | 评估 |
|------|------|
| 改动范围 | `embedding.rs`（文本构造函数 + 生成入口）、`commands/note.rs`（笔记变更后触发重向量化） |
| 数据兼容 | 老向量仍是旧文本生成的，不重建则笔记不参与匹配（无错误，只是效果未生效） |
| 风险 | 低 |
| 工作量 | 约 0.5 天 |

## OPT-05 列表视图：关键字搜索范围过窄

### 现状排查结论

`ListView.tsx:127` 的过滤条件**只匹配项目名称**：

```ts
if (searchQuery && !p.name.toLowerCase().includes(searchQuery.toLowerCase()))
```

描述、URL、语言、AI 摘要、笔记等字段全部不参与关键字匹配。项目多了以后"记得是做什么的但忘了名字"就搜不出来。

### 难度评估：不大

**前端项目对象已包含所需字段**——`get_projects`（`project.rs:12`）是全量 SELECT（含 description、languages、url、ai_summary、runbook、readme_content 等全部大字段），前端只是没用它们过滤。因此：

| 方案 | 范围 | 难度 |
|------|------|------|
| **A. 扩展前端匹配字段**（推荐） | 关键字同时匹配 `name + description + url + languages + ai_summary`（均已在前端内存中，纯前端改动，**零后端改动**） | 低，约 0.5 天 |
| B. 连笔记一起搜 | 需 join `project_notes` 或单独拉取笔记，笔记可能较长 | 中，需要后端配合或单独接口 |
| C. README 全文搜索 | readme_content 字段大（单项目可达数百 KB），前端全文匹配有性能风险；如需要建议走后端 SQL `LIKE` 并延迟加载 | 高，**不建议本期做** |

### 修复方案（采纳方案 A）

1. 关键字匹配字段扩展为：`name`、`description`、`url`、`languages`、`ai_summary`；
2. 搜索框 placeholder 更新为「搜索项目名称、描述、URL、语言…」；
3. （可选增强）命中非名称字段时，在列表行内高亮显示命中字段的片段，让用户知道为什么被搜出来。

### ⚠️ 顺带发现的性能隐患（记录，不在本期范围）

`get_projects` 全量 SELECT 把 `readme_content`、`runbook`、`ai_summary` 等大文本字段一次性拉到前端。项目数到几百上千时内存和首屏加载会有压力。**建议后续单独立项**：列表接口只返回轻量字段，详情打开时再按 id 拉全字段。
