### 2026-07-11 10:46 - Agent - Phase 1 打磨：github_token 防御性修复 + i18n 覆盖率提升

**完成内容**：

### 2026-07-09 架构改进 - 加密密钥跟随仓库

**背景**：
用户提出关键问题：每个仓库的数据库加密密钥应该独立，跟随仓库目录走，而不是全局共享。

**旧方案问题**：
- 加密密钥存在 `app_data_dir/.cryptokey`（全局共享）
- 仓库数据库存在 `vaults/<name>/os_compass.db`
- 多仓库共用同一密钥，复制仓库目录到另一台电脑无法解密敏感数据

**新方案**：
加密密钥文件 `.cryptokey` 放在**仓库目录下**，与 `os_compass.db` 同级：

```
vaults/
├── work/
│   ├── .cryptokey          # 工作仓库的独立密钥
│   ├── os_compass.db       # 工作仓库数据库
│   └── config.json
└── personal/
    ├── .cryptokey          # 个人仓库的独立密钥
    ├── os_compass.db       # 个人仓库数据库
    └── config.json
```

**修改的文件**：

1. **`lib.rs`** - 启动时加载密钥：
   - 记录 `current_vault_dir`（当前仓库目录）
   - 从 `vault_dir/.cryptokey` 加载密钥
   - 兼容旧方案：如果仓库目录没有密钥，从 `app_data_dir/.cryptokey` 迁移
   - 首次启动：在仓库目录生成新密钥

2. **`vault.rs`** - `open_vault()` 切换仓库时：
   - 加载目标仓库的 `.cryptokey`
   - 如果不存在则生成新密钥
   - 调用 `crypto::init_crypto()` 切换密钥

**优势**：
- 每个仓库独立加密，删除仓库时密钥一并删除
- 复制仓库目录到另一台电脑，密钥跟随，可正常解密
- 不同仓库的敏感数据互不影响

**兼容性**：
- 旧的全局 `.cryptokey` 会自动迁移到仓库目录
- 迁移后旧的 `app_data_dir/.cryptokey` 保留但不再使用

在将系统配置从 `config.json` 迁移到 `app_settings` 表时，**未做数据迁移**，导致用户已配置的 LLM API Key、模型、代理等设置全部丢失，进而：
- 项目详情页"重新解析"按钮失效（LlmClient::from_settings() 返回 None）
- "翻译"功能失效（无 API Key 无法调用 LLM）
- "翻译 Releases"功能失效

**根本原因**：
- 修改存储方案时只考虑新用户，未考虑存量用户
- `get_settings()` 只从新表读取，旧 config.json 的数据被无视
- 违反了"改功能不能破坏现有连接功能"的基本原则

**修复措施**：
1. `settings.rs` 的 `get_settings()` 添加**自动迁移逻辑**：
   - 优先从 `app_settings` 表读取
   - 如果表为空，从旧 `config.json` 读取（`%APPDATA%/com.os-compass.os-compass/config.json`）
   - 读取后自动写入 `app_settings` 表，完成迁移
2. 添加 `LegacyConfig` 结构体兼容旧格式

**教训**：
- **任何存储方案变更都必须包含数据迁移**
- 修改前必须梳理所有依赖该存储的功能
- 改不动的东西不要碰，连接功能必须保持可用
