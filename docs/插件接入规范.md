> **二期功能标记**：本规范定义的插件系统为二期（Phase 2）功能。当前 M13 只支持内置插件，M14 扩展为热加载第三方插件。

---

## 1 概述

### 1.1 编写目的

定义 OS-Compass 功能插件（FeaturePlugin）的接入规范，包括插件声明方式、数据库管理模式、生命周期、配置管理、错误处理等。插件开发者按照本规范实现插件，即可被 PluginManager 注册和管理。

### 1.2 适用范围

- M13：内置插件（情报雷达、意图搜索）
- M14：热加载第三方插件（未来）
- 所有 FeaturePlugin 类型的插件

### 1.3 与现有系统的关系

| 概念 | 说明 |
|------|------|
| SourcePlugin | 一期平台扩展（GitHub/Gitee/NPM/PyPI），不走本规范 |
| FeaturePlugin | 二期功能插件（情报雷达、意图搜索、Webhook 等），走本规范 |

## 2 数据库管理模式

### 2.1 四种 DB 模式

插件开发者通过声明 `db_mode` 字段选择数据库管理策略：

| 模式 | db_mode 值 | 说明 | 仓库切换行为 | 适用场景 |
|------|-----------|------|-------------|----------|
| 主库 | `main` | 直接读写主库 os_compass.db | 跟随仓库 | 数据量小、与主库强关联 |
| 全局库 | `global` | 全局固定位置的独立 .db 文件 | 不变（跨仓库共享） | 订阅配置、搜索历史等跨仓库数据 |
| 仓库独立库 | `vault` | 跟随仓库目录的独立 .db 文件 | 跟随仓库（仓库隔离） | 大数据量、与仓库数据关联 |
| 无数据库 | `none` | 不使用数据库 | N/A | 纯通知类插件、无状态插件 |

### 2.2 路径规则表达式

插件通过 `db_path_template` 字段声明数据库文件路径。系统在运行时将变量占位符替换为实际路径。

#### 2.2.1 可用变量

| 变量 | 说明 | 示例值 |
|------|------|--------|
| `${app_data_dir}` | Tauri 应用数据目录 | `C:\Users\xxx\AppData\Roaming\com.os-compass.app` |
| `${vault_dir}` | 当前仓库目录路径 | `D:\MyVaults\Work` |
| `${plugin_id}` | 插件唯一标识 | `radar` / `search` |

#### 2.2.2 各模式的路径规则

| db_mode | db_path_template | 实际路径示例 |
|---------|-----------------|-------------|
| `main` | （不适用，使用主库连接） | 主库 os_compass.db |
| `global` | `${app_data_dir}/plugins/plugin_${plugin_id}.db` | `.../AppData/Roaming/.../plugins/plugin_radar.db` |
| `vault` | `${vault_dir}/plugin_${plugin_id}.db` | `D:\MyVaults\Work\plugin_radar.db` |
| `none` | （不适用） | 无 |

#### 2.2.3 路径解析规则

1. 系统在插件初始化时解析 `db_path_template`
2. 替换所有 `${variable}` 占位符为实际值
3. 确保父目录存在（自动创建）
4. `main` 模式：系统直接提供主库连接，不解析路径
5. `none` 模式：跳过数据库初始化

## 3 插件声明

### 3.1 插件元数据

每个插件通过实现 FeaturePlugin trait 声明自身信息：

```rust
#[async_trait]
pub trait FeaturePlugin: Send + Sync {
    fn id(&self) -> &str;
    fn name(&self) -> &str;
    fn plugin_type(&self) -> FeaturePluginType;
    fn version(&self) -> &str;

    fn db_mode(&self) -> DbMode { DbMode::None }
    fn db_path_template(&self) -> Option<&str> { None }

    async fn init(&self, context: &PluginContext) -> Result<(), PluginError>;
    async fn on_enable(&self, context: &PluginContext) -> Result<(), PluginError>;
    async fn on_disable(&self, context: &PluginContext) -> Result<(), PluginError>;
    async fn execute(&self, context: &PluginContext) -> Result<FeatureResult, PluginError>;
}
```

### 3.2 DbMode 枚举

```rust
pub enum DbMode {
    Main,
    Global,
    Vault,
    None,
}

impl DbMode {
    pub fn as_str(&self) -> &'static str {
        match self {
            DbMode::Main => "main",
            DbMode::Global => "global",
            DbMode::Vault => "vault",
            DbMode::None => "none",
        }
    }
}
```

### 3.3 PluginContext

系统为每个插件构建 PluginContext，包含运行时所需的资源：

```rust
pub struct PluginContext {
    pub vault_dir: PathBuf,
    pub app_data_dir: PathBuf,
    pub config: serde_json::Value,
    pub llm_config: AppSettings,
    pub plugin_db_path: Option<PathBuf>,
}
```

| 字段 | 说明 |
|------|------|
| vault_dir | 当前仓库目录 |
| app_data_dir | 应用数据目录 |
| config | 插件配置 JSON（从 feature_plugins.config 读取） |
| llm_config | LLM 设置（API Key/Base URL/Model 等） |
| plugin_db_path | 插件数据库路径（db_mode 为 main/none 时为 None，由系统解析 db_path_template 得出） |

### 3.4 数据库访问方式

| db_mode | 访问方式 | 说明 |
|---------|----------|------|
| `main` | `crate::db::DATABASE` 全局 | 插件直接通过 DATABASE 全局锁访问主库 |
| `global` | `PluginContext.plugin_db_path` | 插件用 `Connection::open(path)` 打开独立 .db |
| `vault` | `PluginContext.plugin_db_path` | 同上，路径跟随仓库 |
| `none` | 无 | 不提供数据库访问 |

### 3.5 插件数据库表结构管理

- `global` 和 `vault` 模式：插件在 `init()` 中自行创建表结构
- `main` 模式：插件表结构需要在主库 INIT_SCHEMA_SQL 中预定义
- `none` 模式：无表结构管理

## 4 插件生命周期

### 4.1 生命周期阶段

| 阶段 | 触发时机 | 调用方法 | 说明 |
|------|----------|----------|------|
| 注册 | 应用启动 | PluginRegistry.register() | 内置插件静态注册，M14 支持动态注册 |
| 初始化 | 注册后 | init() | 初始化表结构、加载配置 |
| 启用 | 用户开启 | on_enable() | 启动后台任务（如定时扫描） |
| 禁用 | 用户关闭 | on_disable() | 停止后台任务，保留数据 |
| 执行 | 用户触发/定时 | execute() | 执行插件功能 |
| 仓库切换 | 用户切换仓库 | on_disable() → init() → on_enable()（如已启用） | 重新加载新仓库的插件数据 |

### 4.2 启动流程

```
应用启动
  → PluginRegistry.register_builtin()
  → 遍历所有已注册插件
    → 解析 db_mode 和 db_path_template
    → 构建 PluginContext（含 plugin_db_path）
    → 调用 plugin.init(context)
    → 查询 feature_plugins.enabled
    → 如果 enabled=true → 调用 plugin.on_enable(context)
```

### 4.3 仓库切换流程

```
用户切换仓库
  → 遍历所有已启用插件
    → 调用 plugin.on_disable(context)   // 停止旧仓库的后台任务
  → 切换主库 DATABASE
  → 遍历所有已注册插件
    → 重新解析 db_path_template（vault_dir 已变化）
    → 构建 new PluginContext
    → 调用 plugin.init(new_context)     // 初始化新仓库的插件库
    → 如果 enabled=true → 调用 plugin.on_enable(new_context)
```

> **注意**：`global` 模式的插件在仓库切换时，plugin_db_path 不变（路径用 `${app_data_dir}` 而非 `${vault_dir}`），但仍需 on_disable/on_enable 以暂停和恢复后台任务。

## 5 配置管理

### 5.1 配置存储

插件配置存储在主库 `feature_plugins` 表的 `config` 字段（JSON 字符串）。

### 5.2 配置读写 API

| 方法 | 说明 |
|------|------|
| `PluginManager.get_config(plugin_id)` | 读取插件配置 JSON |
| `PluginManager.save_config(plugin_id, config)` | 保存插件配置 JSON |
| `PluginContext.config` | 插件运行时从 config 字段获取配置 |

### 5.3 配置结构

插件自行定义配置 JSON 结构。建议约定：

```json
{
  "check_interval": 86400,
  "ttl_enabled": false,
  "ttl_days": 30,
  "web_search_strategy": "github_search",
  "notification_enabled": true
}
```

## 6 错误处理

### 6.1 PluginError 类型

```rust
pub enum PluginError {
    NotSupported(String),
    NotFound(String),
    InitFailed(String),
    ExecutionFailed(String),
    DbError(String),
    ConfigError(String),
}
```

### 6.2 错误处理策略

| 场景 | 处理方式 |
|------|----------|
| init() 失败 | 记录日志，插件标记为"初始化失败"，不执行 on_enable |
| on_enable() 失败 | 回滚 enabled 状态为 false，提示用户 |
| on_disable() 失败 | 记录日志，强制标记 enabled=false |
| execute() 失败 | 返回 FeatureResult { status: Failed }，提示用户 |
| DB 打开失败 | 返回 DbError，插件不可用 |

## 7 插件清单文件（M14 预留）

M14 热加载时，第三方插件需要提供清单文件描述插件元数据：

```json
{
  "id": "radar",
  "name": "情报雷达",
  "type": "radar",
  "version": "1.0.0",
  "db_mode": "vault",
  "db_path_template": "${vault_dir}/plugin_${plugin_id}.db",
  "entry_point": "libradar_plugin.dll"
}
```

M13 内置插件不需要清单文件（元数据通过 trait 方法直接返回）。

## 8 插件分类与存储架构

### 8.1 两类插件

| 分类 | 说明 | 生命周期 | 配置存储 | 业务数据存储 |
|------|------|----------|----------|--------------|
| 系统级插件 | 系统默认加载，全局存在 | 随应用启动，不受仓库切换影响 | `${AppData}\.os-compass\plugins.db` | 跟随 db_mode |
| 仓库级插件 | 只在特定仓库加载 | 依赖仓库，切换仓库时重新加载 | 跟随仓库 | 跟随 db_mode |

### 8.2 存储目录结构

```
跨平台统一配置目录：${AppData}\.os-compass\
├── plugins.db              ← 系统级插件配置库
│   └── system_plugins 表  ← id, name, type, version, enabled, config
│
${AppData}\com.os-compass.app\
├── os_compass.db           ← 主数据库（项目数据）
├── settings.db             ← 应用设置
└── plugins/                ← 插件业务数据目录
    └── plugin_*.db         ← 按 db_mode 存放

仓库目录 ${vault_dir}\
├── projects/              ← 克隆的项目
└── plugin_*.db            ← vault 模式插件业务数据
```

### 8.3 跨平台路径变量

| 变量 | Windows | macOS | Linux |
|------|---------|-------|-------|
| `${AppData}` | `C:\Users\xxx\AppData\Roaming` | `/Users/xxx/Library/Application Support` | `/home/xxx/.config` |

### 8.4 设计原则

1. **用户配置 vs 程序数据分离**：
   - `${AppData}\.os-compass\` = 用户插件配置（可跨设备同步）
   - `${AppData}\com.os-compass.app\` = 程序运行数据
2. **系统级 vs 仓库级分离**：
   - 系统级插件配置独立存储，与主库解耦
   - 仓库级插件配置跟随仓库目录
3. **db_mode 决定业务数据位置**，不影响配置存储位置

### 8.5 操作域层次

插件系统采用三层操作域设计，确保配置独立性与运行时依赖的平衡：

```
┌─────────────────────────────────────────────────────────┐
│  插件域（系统级）                                       │
│  ├── 插件元数据（id, name, type, version）            │
│  ├── 启用状态（enabled）                              │
│  └── 插件配置（config JSON）                          │
│  📍 存储：${AppData}/.os-compass/plugins.db         │
│  🔄 生命周期：随应用启动，不受仓库切换影响            │
└─────────────────────────────────────────────────────────┘
                          │
                          │ 运行时注入
                          ▼
┌─────────────────────────────────────────────────────────┐
│  仓库域（当前仓库）                                    │
│  ├── LLM 配置（API Base, API Key, Model）            │
│  ├── 翻译配置                                         │
│  ├── GitHub Token / Gitee Token                       │
│  ├── 爬虫代理配置                                     │
│  └── 其他系统变量                                     │
│  📍 存储：当前仓库的 os_compass.db                   │
│  🔄 生命周期：跟随仓库，切换仓库时变化                │
└─────────────────────────────────────────────────────────┘
                          │
                          │ 插件执行时使用
                          ▼
┌─────────────────────────────────────────────────────────┐
│  业务域（跟随仓库）                                    │
│  ├── 订阅源数据（radar_sources）                      │
│  ├── 扫描结果（radar_items）                         │
│  ├── 搜索缓存（search_cache）                         │
│  └── 搜索历史（search_history）                        │
│  📍 存储：{vault_dir}/plugin_*.db                    │
│  🔄 生命周期：跟随仓库，数据可迁移                    │
└─────────────────────────────────────────────────────────┘
```

#### PluginContext 结构

```rust
pub struct PluginContext {
    /// 插件域：插件自己的配置（来自 plugins.db）
    pub config: serde_json::Value,

    /// 仓库域：当前仓库的 LLM 配置
    pub llm_config: serde_json::Value,

    /// 仓库域：代理配置
    pub proxy_config: serde_json::Value,

    /// 业务域：插件数据库路径
    pub plugin_db_path: Option<PathBuf>,

    /// 目录信息
    pub vault_dir: PathBuf,
    pub app_data_dir: PathBuf,
}
```

#### 域依赖关系

| 域 | 数据来源 | 可写性 | 跨仓库 |
|----|---------|--------|--------|
| 插件域 | `${AppData}/.os-compass/plugins.db` | ✅ 插件运行时可修改 | ❌ 系统级 |
| 仓库域 | 当前仓库 `os_compass.db` | ❌ 只读 | ❌ 跟随仓库 |
| 业务域 | `{vault_dir}/plugin_*.db` | ✅ 插件运行时写入 | ❌ 跟随仓库 |

## 9 安全约束

- 插件不能直接访问其他插件的数据库
- 插件通过 PluginContext 访问主库时，应只读写与自身功能相关的表
- 插件配置中不应存储明文密钥（使用 system_variables 加密存储）
- 系统级插件配置存储在 `${AppData}\.os-compass\plugins.db`，插件不应直接修改

## 10 内置插件 DB 模式声明

| 插件 | db_mode | db_path_template | 理由 |
|------|---------|-----------------|------|
| 情报雷达（Radar） | vault | `${vault_dir}/plugin_${plugin_id}.db` | 雷达条目与仓库项目关联，仓库隔离 |
| 意图搜索（Search） | vault | `${vault_dir}/plugin_${plugin_id}.db` | 搜索缓存与仓库项目关联，仓库隔离 |

> 未来如果搜索历史需要跨仓库共享，可切换为 `global` 模式。
