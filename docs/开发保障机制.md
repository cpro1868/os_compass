## 一、问题根因分析

### 今日交付问题

| 问题 | 根因 | 教训 |
|------|------|------|
| 雷达删除无确认 | 没检查危险操作 | 删除操作必须加确认 |
| 英文提示硬编码 | 没检查 i18n 覆盖 | 用户可见文本必须 i18n |
| 仓库路径混乱 | 硬编码+API误用 | 路径必须统一管理 |
| 理解偏差 | 没复述需求确认 | 编码前必须确认理解 |

### 根因总结

1. **流程缺失**：编码前没有检查环节
2. **规范缺失**：没有危险操作规范
3. **工具缺失**：没有统一路径管理

## 二、保障机制分层

| 阶段 | 工具/Skill | 目的 | 触发时机 |
|------|------------|------|----------|
| 需求理解 | brainstorming | 确保理解正确需求 | 新功能、大改动 |
| 编码前检查 | Pre-Coding Check | 发现潜在问题 | 每个任务开始前 |
| 编码中保障 | 编译即时检查 | 及时发现问题 | 编码过程中 |
| 提交前验证 | verification-before-completion | 确保代码质量 | 每次提交前 |
| 问题排查 | systematic-debugging | 系统性排查问题 | 遇到 Bug 时 |
| 代码审查 | requesting/receiving-code-review | 发现潜在问题 | 重要功能完成时 |
| 实施后复盘 | 复盘模板 | 总结经验改进 | 任务完成后 |

### 阶段 2：编码前检查（Pre-Coding Check）

**目的**：在动手前发现潜在问题

#### 2.1 危险操作检查

| 操作类型 | 必须检查项 |
|----------|-----------|
| 删除（Delete） | 必须有确认对话框 |
| 覆盖（Overwrite） | 必须有备份/版本控制 |
| 迁移（Migration） | 必须有回滚方案 |

**模板**：
```
⚠️ 危险操作检查
操作：delete_item
风险：误删无法恢复
措施：添加 confirm 对话框
```

#### 2.2 i18n 检查

| 类型 | 必须检查项 |
|------|-----------|
| 按钮文本 | 必须使用 t('xxx') |
| 提示信息 | 必须使用 t('xxx') |
| 错误信息 | 必须使用 t('xxx') |
| 常量文本 | 必须使用 i18n 键 |

**模板**：
```
⚠️ i18n 检查
文本："Delete success" → t('radar.deletedSuccess')
文本："Are you sure?" → t('common.confirmDelete')
```

#### 2.3 硬编码检查

| 类型 | 必须检查项 |
|------|-----------|
| 文件路径 | 必须通过 AppPaths 获取 |
| 文件名 | 必须通过配置获取 |
| 目录名 | 必须通过常量定义 |
| URL | 必须通过配置获取 |

**模板**：
```
⚠️ 硬编码检查
硬编码："os_compass.db" → AppPaths::vault_db_name()
硬编码：".cryptokey" → AppPaths::vault_key_name()
```

#### 2.4 现有实现检查

| 检查项 | 说明 |
|--------|------|
| 已有模块 | 是否已有类似功能 |
| 复用可能 | 能否复用现有代码 |
| 扩展方式 | 是扩展还是新建 |

**模板**：
```
⚠️ 现有实现检查
已有：vault.rs 有路径管理
复用：使用 AppPaths 模块
扩展：添加新方法
```

#### 2.5 影响范围检查

| 检查项 | 说明 |
|--------|------|
| 修改文件 | 哪些文件会被修改 |
| 影响模块 | 哪些模块会受影响 |
| 测试重点 | 需要重点测试什么 |

### 阶段 3：编码中保障（In-Coding Guard）

**目的**：编码过程中及时发现问题

#### 3.1 编译检查

每完成一个功能模块后立即运行：
```bash
cargo check
pnpm typecheck
```

#### 3.2 危险操作即时检查

| 检查点 | 说明 |
|--------|------|
| 删除函数 | 检查是否有确认调用 |
| 数据库写入 | 检查是否在事务中 |
| 敏感操作 | 检查是否有日志 |

---

### 阶段 4：提交前验证（Pre-Commit Check）

**目的**：确保提交的代码质量

#### 4.1 必须使用 verification-before-completion Skill

**触发条件**：每次声称完成时

**要求**：
- 运行验证命令
- 确认输出结果
- 有证据才能声称成功

#### 4.2 必须验证项

| 验证项 | 命令 |
|--------|------|
| Rust 编译 | `cargo check --lib` |
| TypeScript 类型 | `pnpm typecheck` |
| 前端构建 | `pnpm build` |

#### 4.3 功能验证清单

| 模块 | 验证点 |
|------|--------|
| 删除功能 | 点击删除 → 弹出确认 → 点击确认 → 执行删除 |
| i18n | 切换语言 → 文本正确显示 |
| 路径 | 检查文件实际位置与预期一致 |

#### 4.4 提交信息规范

```
<类型>: <简短描述>

<详细描述（可选）>

<关联Issue（可选）>
```

类型：`feat` | `fix` | `docs` | `chore` | `refactor`

---

### 阶段 5：问题排查（Problem Investigation）

**目的**：遇到问题时系统性地排查

#### 5.1 必须使用 systematic-debugging Skill

**触发条件**：遇到 Bug、测试失败、异常行为时

**要求**：
- 不急于修复，先理解问题
- 按 Skill 指引系统性排查
- 有证据才能定位根因

#### 5.2 问题记录模板

```
## 问题描述
-

## 排查过程
1. 复现问题
2. 定位相关代码
3. 分析根因
4. 验证假设

## 解决方案
-

## 教训
-
```

---

### 阶段 6：代码审查（Code Review）

**目的**：通过审查发现潜在问题

#### 6.1 使用 requesting-code-review Skill

**触发条件**：重要功能完成时

#### 6.2 使用 receiving-code-review Skill

**触发条件**：收到审查反馈时

**要求**：
- 不盲目接受建议
- 技术验证优先
- 有疑问先确认

---

### 阶段 7：实施后复盘（Post-Implementation Review）

**目的**：总结经验，持续改进

| 检查项 | 说明 |
|--------|------|
| 问题记录 | 遇到什么问题 |
| 解决方案 | 怎么解决的 |
| 教训总结 | 下次如何避免 |

## 四、质量门禁

### 必须通过才能提交

1. ✅ `cargo check --lib` 无错误
2. ✅ `pnpm typecheck` 无错误
3. ✅ `pnpm build` 成功

### 必须检查才能编码

1. ⚠️ 危险操作有确认
2. ⚠️ 所有文本通过 i18n
3. ⚠️ 无硬编码路径/文件名
4. ⚠️ 复用现有代码

## 五、工具支持

### 预提交检查脚本

```powershell
# scripts/pre-commit-check.ps1
Write-Host "Running pre-commit checks..."

# Rust 检查
cargo check --lib
if ($LASTEXITCODE -ne 0) { exit 1 }

# TypeScript 检查
pnpm typecheck
if ($LASTEXITCODE -ne 0) { exit 1 }

# 构建检查
pnpm build
if ($LASTEXITCODE -ne 0) { exit 1 }

Write-Host "All checks passed!"
```

### 使用方式

```bash
# 提交前运行
powershell -ExecutionPolicy Bypass -File scripts/pre-commit-check.ps1
```
