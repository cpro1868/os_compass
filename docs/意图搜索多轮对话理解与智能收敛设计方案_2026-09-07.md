> 日期：2026-09-07 15:48  
> 状态：📋 设计文档（实施前确认）  
> 目标：彻底解决意图搜索“无上下文记忆、追问废话、前言不搭后语、陷入死循环”问题。

---

## 一、现状缺陷与目标对比

| 对比维度 | 现状（问题现象） | 改进后（目标表现） |
|---|---|---|
| **上下文感知** | **完全无状态**：每轮交互仅传当前单句，LLM 孤立分析用户输入的字面量。 | **全流程记忆**：完整传递最近轮次的对话上下文（用户输入 + 助手追问）。 |
| **短语理解** | 看到“不限”、“完整应用”脱离前文，反问“你想构建什么完整应用”。 | 结合上文追问，准确识别“不限”是回答语言偏好，“完整应用”是回答形态偏好。 |
| **收敛判断** | 缺乏收敛机制，容易反复判定为 `unclear`，造成无休止发问。 | **动态评估信息饱和度**：一旦核心领域与关键偏好齐备，立即收敛并发起精准搜索。 |
| **追问质量** | 模板化、泛化发问，与上下文脱节。 | 紧扣前文未定维度发问（如“更侧重录制推流还是离线剪辑”），不发散。 |

### 1. 数据结构协议 (`src/api/search.ts` & Rust 侧)

新增通用的对话消息结构，支持上下文序列化。

#### TS 类型定义：
```typescript
export interface SearchContextMessage {
  role: 'user' | 'assistant';
  content: string;
}

// analyzeIntent 接口增加可选的上下文参数
export async function analyzeIntent(
  userInput: string,
  history?: SearchContextMessage[]
): Promise<IntentAnalysis> {
  return invoke<IntentAnalysis>('analyze_user_intent', { userInput, history });
}
```

#### Rust 结构体定义 (`commands/search_cmd.rs` / `plugins/search.rs`)：
```rust
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct SearchContextMessage {
    pub role: String,
    pub content: String,
}
```

### 2. 前端上下文组装 (`src/components/SearchView.tsx`)

#### 修改点：
在 `handleSubmit` 调用 `analyzeIntent` 时，不再只传孤立的 `query`，而是自动提取当前会话中最近的有效对话（最多取最近 6 条）：

```typescript
// 具象代码逻辑：
const history: SearchContextMessage[] = messages
  .filter(msg => msg.phase === 'idle' || !msg.phase) // 过滤掉加载状态中的废消息
  .slice(-6) // 取最近上下文
  .map(msg => ({
    role: msg.role,
    content: msg.content || (msg.clarification ? msg.clarification.questions?.join(' ') : '')
  }))
  .filter(item => item.content.trim().length > 0);

intent = await withTimeout(analyzeIntent(query, history), 30000);
```

同时，当多轮沉淀出明确意图后，搜索摘要展示更加连贯，避免页面状态突兀刷新。

### 3. 后端命令层 (`commands/search_cmd.rs`)

#### 修改点：
`analyze_user_intent` 命令接收 `history` 参数，并转发给核心业务层：

pub async fn analyze_user_intent(

### 4. 核心意图大脑与 System Prompt 重构 (`plugins/search.rs`)

这是本次升级的最核心部分，将机械分类器重塑为**具备记忆与收敛能力的开源架构顾问**。

#### System Prompt 具象设计：
```markdown
你是一个顶尖的开源项目选型顾问与系统架构师。
你的职责是：结合用户历史对话上下文，深入理解用户的真实意图，准确提取用于在 GitHub/Gitee 及本地知识库中检索项目的关键词。

【对话历史上下文】：
{formatted_history}

【用户当前输入】：
「{user_input}」

【意图理解核心规则】：
1. 承接上下文（Context Grounding）：
   - 用户回答的简短词汇（如“完整应用”、“不限”、“Python”、“轻量级”）必须结合上文助手的提问理解。
   - 严禁脱离最初讨论的业务领域（例如前文已确认为“视频制作/处理”，用户的“完整应用”必须理解为“视频制作/剪辑的完整桌面或网页应用”，绝对禁止跳转到“通用应用开发”）。

2. 智能收敛判断（Convergence）：
   - 若当前已知信息（领域 + 用户偏好）已经足够锁定一批有代表性的知名开源项目（如：“视频处理 + 完整应用”已非常充分，足以为其匹配 Shotcut、HandBrake、OBS、OpenShot 等），必须判定为 "clear"，立即进入搜索！
   - 严禁就“技术栈”、“使用场景”等次要问题无休止发问。

3. 追问纪律（Clarification Policy）：
   - 仅在用户初次提问极端宽泛（如“求推荐项目”、“有啥好玩的”），且无法提供任何有效项目时，才判定为 "unclear"。
   - 追问的问题必须紧扣当前未决的关键分歧，且必须承接上文。
   - 追问最多允许 1~2 个关键维度选项，严禁提问“您想用什么语言构建应用”这类开发型废话。

【输出要求】：
必须返回严格的 JSON，禁止任何 Markdown 格式或额外解释：
如果是明确意图（信息已足够搜索）：
{
  "intent": "clear",
  "intent_type": "领域/需求类型（如：视频剪辑完整桌面应用）",
  "keywords": ["核心关键词1", "核心关键词2", "核心关键词3"],
  "summary": "一句话向用户说明：已结合您前述的视频处理与完整应用需求，正在为您匹配项目..."
}

如果确实信息严重匮乏必须澄清：
{
  "intent": "unclear",
  "questions": ["承接上文的针对性问题（如：您更倾向于录制推流类，还是后期剪辑与格式转换类？）"],
  "options": ["剪辑与特效制作", "转码与格式处理", "推流与屏幕录制"]
}
```

## 三、真实场景模拟预期对比

以您刚才遇到的案例走查：

1. **用户**：“你好，给我推荐一款视频制作类工具”
   - **系统**：判定领域宽泛，追问剪辑/转码/录制（正常追问第 1 轮）。
2. **用户**：“面向视频处理”
   - **系统**：记录【领域：视频处理】，追问形态是开发库还是直接可用的应用。
3. **用户**：“不限”
   - **系统**（具备记忆）：识别“不限”针对的是语言平台，继续保留【视频处理】画像。
4. **用户**：“完整应用”
   - **系统（智能收敛触发）**：
     - 上下文综合画像：`视频制作 + 视频处理 + 完整独立应用 + 语言不限`。
     - **收敛判定**：信息极其饱和！足以匹配 Shotcut、LosslessCut、HandBrake、OBS Studio 等知名项目。
     - **输出**：`intent: "clear"`，提取关键词 `["视频剪辑", "视频处理", "桌面应用", "转码"]`，**立即结束追问，直接展示搜索结果！**
