## 1. 问题背景

在 OS-Compass 项目开发过程中，存在以下客观挑战：

- **网络不稳定**：可能导致 Agent 会话意外中断
- **Tokens 消耗快**：长上下文会话可能触发限制或断开
- **多 Agent / 多 Session / 多客户端**：同一项目可能在不同工具、不同窗口中继续
- **开发工具多样性**：可能使用 Kimi Code、OpenCode、Cursor、Copilot、Claude Code 等不同 AI 编程助手

这些挑战的核心风险是：**当前会话的上下文丢失后，新会话如何快速、准确地接续工作？**

## 2. 核心原则

### 2.1 文件系统是唯一持久状态

> **Agent 的记忆只存在于当前会话，文件系统才是唯一真相来源。**

所有设计决策、代码变更、任务状态、验证结果必须写入文件。新 Agent 不应该依赖前一个 Agent 的内存，而应该通过阅读文件恢复上下文。

### 2.2 状态必须显式化

> **不要依赖隐式上下文，所有状态必须显式记录。**

- 当前在做什么？→ 写入 `CONTEXT.md` / `CURRENT-TASK.md`
- 完成了什么？→ 追加到 `docs/工作进展记录.md`
- 还有什么没做？→ 写入 TODO 文件
- 遇到了什么问题？→ 写入 `docs/工作进展记录.md` 的遗留问题

### 2.3 任务必须原子化

> **每个会话只处理一个可独立完成的小任务。**

- 单个任务应在 30-120 分钟内完成
- 任务完成后必须验证并记录
- 避免一个巨大任务跨越多个会话

### 2.4 恢复成本最小化

> **新 Agent 通过阅读 3 个文件，就能恢复 80% 的上下文。**

这三个文件是：
1. `CONTEXT.md` — 项目整体状态和当前任务
2. `docs/工作进展记录.md` — 最近做了什么
3. `docs/里程碑和开发计划.md` — 接下来该做什么

### 2.5 工具无关性

> **关键上下文文件必须位于根目录，不依赖任何特定 Agent 工具或隐藏目录。**

- 不使用仅 Kimi 识别的 `.kimi-code/` 目录作为主要上下文载体
- 使用根目录的 `AGENTS.md`、`CONTEXT.md`、`CURRENT-TASK.md`、`SESSION-LOG.md`
- 任何 AI 工具（Kimi Code、OpenCode、Cursor、Claude Code 等）打开项目都能立即看到这些文件
- `.kimi-code/` 目录仅作为 Kimi 特定配置的补充，不作为上下文恢复的主要依赖

## 3. 机制设计

### 3.1 三层上下文恢复体系

```
┌─────────────────────────────────────────────────────────────┐
│  第一层：项目级上下文（长期稳定，位于根目录）                   │
│  - AGENTS.md          ← Agent 协作指南（任何工具打开都可见）   │
│  - README.md          ← 项目介绍 + 新会话必读提示             │
│  - CONTEXT.md         ← 项目快速上下文                        │
│  - docs/里程碑和开发计划.md                                   │
│  - docs/WBS分解.md                                           │
└─────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────┐
│  第二层：会话级上下文（当前迭代）                              │
│  - docs/工作进展记录.md                                       │
│  - CURRENT-TASK.md                                │
│  - SESSION-LOG.md                                 │
└─────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────┐
│  第三层：任务级上下文（原子任务）                              │
│  - TodoList 工具状态                                          │
│  - 当前编辑的文件                                              │
│  - 测试命令和验证结果                                          │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 关键文件说明

#### 3.2.0 `AGENTS.md`（根目录）⭐

**作用**：所有 AI Agent 的首要必读文件。无论使用 Kimi Code、OpenCode、Cursor、Copilot、Claude Code 还是其他工具，打开项目后都应首先阅读本文件。

**内容**：
- 项目简介
- 新会话恢复流程
- 工作规范
- 关键文件索引
- 安全红线
- 技术约束

#### 3.2.1 `CONTEXT.md`（根目录）

**作用**：项目快速上下文入口，新 Agent 首先阅读。

**更新时机**：
- 项目重大决策变更
- 里程碑完成
- 当前任务切换

#### 3.2.2 `docs/工作进展记录.md`

**作用**：持续记录每次工作会话的成果和状态。

**更新规则**：
- 每次会话结束必须追加一条记录
- 即使会话异常中断，也应在恢复后补录
- 新记录追加到文件最上方

#### 3.2.3 `CURRENT-TASK.md`

**作用**：显式记录当前正在进行的任务状态。

**更新时机**：
- 开始新任务时创建/更新
- 任务状态变化时更新
- 任务完成时标记为 done

#### 3.2.4 `SESSION-LOG.md`

**作用**：记录当前会话的详细操作日志，便于排查和恢复。

**更新时机**：
- 会话中每完成一个关键步骤追加
- 出现异常时记录错误信息

### 3.3 原子任务管理

#### 3.3.1 任务拆分原则

| 原则 | 说明 |
|------|------|
| 单一目标 | 每个任务只解决一个问题 |
| 可验证 | 任务完成有明确的验收标准 |
| 可回滚 | 任务变更最好能通过 git 回滚 |
| 短周期 | 理想情况下 30-120 分钟内完成 |

#### 3.3.2 任务执行流程

```
开始任务
  ↓
创建/更新 CURRENT-TASK.md
  ↓
更新 TodoList（工具级跟踪）
  ↓
执行具体工作（读文件 → 编辑 → 测试 → 验证）
  ↓
记录变更到 session-log.md
  ↓
验证通过 → 追加到 docs/工作进展记录.md
  ↓
更新 CONTEXT.md（如里程碑/阶段变化）
  ↓
提交 git / 创建检查点
```

### 3.4 检查点机制（Checkpoint）

位置：`checkpoints/YYYY-MM-DD_HH-MM_检查点名称.md`

内容结构：
- 时间
- 前置状态
- 已完成
- 当前代码状态
- 验证情况
- 回滚方式
- 下一步

### 3.5 版本控制策略

- 每个原子任务完成后立即提交
- 分支策略：`main` + `feature/*` + `design/*` + `hotfix/*`
- 多 Agent 并行时使用 Git Worktree

### 3.6 多工具兼容性

- 不使用只有某个 Agent 能理解的特殊标记
- 所有文档使用 Markdown
- 新 Agent 启动时按标准流程读取文件

## 4. 操作规范

### 4.1 会话开始规范

每次新会话开始时，Agent 必须：

1. **读取 AGENTS.md**
2. **读取 CONTEXT.md**
3. **读取 CURRENT-TASK.md**
4. **读取 docs/工作进展记录.md**
5. 如果 `CURRENT-TASK.md` 状态为 `done`，则从里程碑计划中选择下一个任务
6. 更新 `CURRENT-TASK.md` 为新的当前任务

### 4.2 会话结束规范

每次会话结束前，Agent 必须：

1. **完成当前原子任务**，或明确记录未完成状态
2. **验证**已完成的工作
3. **追加 docs/工作进展记录.md**
4. **更新 CURRENT-TASK.md** 状态
5. **如有必要，更新 CONTEXT.md**
6. **创建检查点**（如果完成重要节点）
7. **执行 git commit**（如果有代码/文档变更）

### 4.3 会话异常中断恢复流程

```
会话意外断开
  ↓
新会话启动
  ↓
读取 CONTEXT.md
  ↓
读取 docs/工作进展记录.md 最新记录
  ↓
读取 CURRENT-TASK.md
  ↓
判断任务状态：
  ├─ 已完成 → 标记 done，选择下一个任务
  ├─ 未完成 → 继续执行
  └─ 不确定 → 检查 git status 和 session-log.md
  ↓
恢复工作
```

## 5. 应急恢复模板

新 Agent 接入时的标准提示词：

```markdown
你正在继续开发 OS-Compass 项目。

请按以下顺序读取文件以恢复上下文：
1. AGENTS.md
2. CONTEXT.md
3. CURRENT-TASK.md
4. docs/工作进展记录.md（最近 3-5 条）
5. docs/里程碑和开发计划.md

当前任务状态见 CURRENT-TASK.md。
请继续执行当前任务，或如果当前任务已完成，则从里程碑计划中选择下一个任务。

注意：
- 所有工作成果必须写入文件
- 每次会话结束必须追加 docs/工作进展记录.md
- 敏感信息不得写入任何文件
```
